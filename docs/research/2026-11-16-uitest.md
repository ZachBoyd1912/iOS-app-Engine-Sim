# Research: uitest (16/11/2026, Haiku 5.5 agent, read-only; verify items marked UNVERIFIED)

## Findings (research only, no files edited)

**Summary:** Tests and screenshots on macos-26 are feasible. Use XCUITest with launch arguments that seed a named state, `performAccessibilityAudit(.all minus macOS-only types)` per screen, and `xcrun xcresulttool export attachments` to pull the screenshots. Motion and haptics are not usable in the Simulator, so both need injected fakes and guards. The main unverified risks are RealityKit rendering on the hosted VM and the missing iOS 18 runtime.

### 1. XCUITest, launch-state seeding, screenshots, export
- **Launch arguments:** `XCUIApplication.launchArguments` can be set before `launch()`. Changes apply only to the next launch ([launchArguments](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/launcharguments.md)). The app reads them with `ProcessInfo.processInfo.arguments`. Example: `-uitest-state settings -seed basic`. `launchEnvironment` is standard XCTest API, but I could not retrieve its page, so it is UNVERIFIED. The local `ios-simulator` skill also documents launch args via `simctl launch` ([C:/Users/zboyd/.claude/skills/ios-simulator/SKILL.md](C:/Users/zboyd/.claude/skills/ios-simulator/SKILL.md)).
- **Screenshots:** `XCTAttachment(screenshot: XCUIScreenshot)` is verified ([XCTAttachment](https://developer.apple.com/documentation/xctest/xctattachment.md)). Get the screenshot from `XCUIScreen.main.screenshot()`, which is standard API and UNVERIFIED on this page. Attach with `add(_:)`. `lifetime` is `.keepAlways` or `.deleteOnSuccess` (case names from memory, UNVERIFIED).
- **Export:** `xcrun xcresulttool export attachments --path X.xcresult --output-path DIR [--test-id …] [--only-failures]` is documented in a third-party mirror of Apple's man page ([xcresulttool(1)](https://keith.github.io/xcode-man-pages/xcresulttool.1.html)). `--output-path` is a directory. The `manifest.json` name mapping is UNVERIFIED on Xcode 26.
- **xcparse:** Its README gives `xcparse screenshots --os --model --test-plan-config <xcresult> <outdir>` and `xcparse attachments <xcresult> <outdir> --uti public.image`, and says it supports "Xcode 11+ xcresult" ([ChargePoint/xcparse](https://github.com/ChargePoint/xcparse)). Xcode 26 compatibility is UNVERIFIED. Prefer the native command and keep xcparse as a fallback.
- **Forum signal:** Apple forum threads report that the old `xcresulttool get --format json` is deprecated and that `--legacy` is a workaround ([thread 763050](https://developer.apple.com/forums/thread/763050), search snippet only, UNVERIFIED).
- **Per-device targets:** The macos-26 image lists simulators iPhone 17 Pro Max, iPhone 17 Pro and iPad Pro 13-inch (M5) on iOS 26.2/26.4/26.5 ([runner-images macos-26-arm64](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md)).
- **App Store sizes:** 6.3-inch is required and accepts 1206×2622. 6.9-inch is listed as not required and accepts 1320×2868. iPad 13-inch accepts 2064×2752 or 2048×2732, and is required only if the app runs on iPad ([App Store Connect screenshot specs](https://developer.apple.com/help/app-store-connect/reference/screenshot-specifications)). Check the exported PNG pixel sizes against these; that check is not verified.

### 2. `performAccessibilityAudit`
- **Signature and availability:** `@MainActor func performAccessibilityAudit(for auditTypes: XCUIAccessibilityAuditType = .all, _ issueHandler: ((XCUIAccessibilityAuditIssue) throws -> Bool)? = nil) throws`. Available from iOS 17, macOS 14 and Xcode 16.3 ([performAccessibilityAudit](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/performaccessibilityaudit(for:_:).md)).
- **Audit types:** `action`, `all`, `contrast`, `dynamicType`, `elementDetection`, `hitRegion`, `parentChild`, `sufficientElementDescription`, `textClipped`, `trait` ([XCUIAccessibilityAuditType](https://developer.apple.com/documentation/xcuiautomation/xcuiaccessibilityaudittype.md)).
- **Platform split:** Apple lists `parentChild` and `action` as macOS-only. The rest apply to iOS ([Performing accessibility audits](https://developer.apple.com/documentation/accessibility/performing-accessibility-audits-for-your-app.md)). On iOS, use `.all.subtracting([.parentChild, .action])` or an explicit list. Passing macOS-only types on iOS is UNVERIFIED.
- **Limits:** It audits the current screen only, so each named state needs its own call. A failing audit fails the test automatically. Apple states that passing the audit "doesn't guarantee a fully accessible app" and that VoiceOver testing is still needed (same Apple article above).
- **Issue handler:** It returns `Bool`. Whether `true` means "ignore" is UNVERIFIED. The issue properties `auditType` and `element` come from a third-party snippet, UNVERIFIED.
- **Repo note:** The local `ios-accessibility` skill's example calls `performAccessibilityAudit(for: [.action])` ([C:/Users/zboyd/.claude/skills/ios-accessibility/references/a11y-patterns.md](C:/Users/zboyd/.claude/skills/ios-accessibility/references/a11y-patterns.md), line 383). `.action` is macOS-only per Apple, so do not copy that example for iOS.

### 3. CoreMotion in the Simulator
- **Simulator:** The only primary source is Apple's retired guide, which says "Motion support (accelerometer and gyroscope) are unsupported" as of iOS 8.2 ([Testing on the iOS Simulator](https://developer.apple.com/library/archive/documentation/IDEs/Conceptual/iOS_Simulator_Guide/TestingontheiOSSimulator/TestingontheiOSSimulator.html)). Xcode 26 behaviour is UNVERIFIED. The local `ios-simulator` skill's limitations table also says "No motion sensor support" ([C:/Users/zboyd/.claude/skills/ios-simulator/SKILL.md](C:/Users/zboyd/.claude/skills/ios-simulator/SKILL.md)).
- **API behaviour:** `isDeviceMotionAvailable` is true only when the device has both an accelerometer and a gyroscope ([isDeviceMotionAvailable](https://developer.apple.com/documentation/coremotion/cmmotionmanager/isdevicemotionavailable.md)). Calling a start method for unavailable hardware "has no effect" ([CMMotionManager](https://developer.apple.com/documentation/coremotion/cmmotionmanager.md)).
- **Design:** Put a `TiltSource` protocol in front of CoreMotion. The real implementation reads `CMMotionManager.deviceMotion`. A fake, selected by a launch argument, drives tilt from scripted values. If `isDeviceMotionAvailable` is false, fall back to on-screen steer controls or touch drag. Do not let the game wait on a motion callback.

### 4. Core Haptics in the Simulator
- **Apple's statement:** WWDC21 session 10278 says "The simulator doesn't work for haptics. You need a physical iPhone 8 or newer to feel the haptics" ([WWDC21 10278](https://developer.apple.com/videos/play/wwdc2021/10278/)). Whether the Simulator throws or silently no-ops is not stated, and the "silent no-op" claim from third parties is UNVERIFIED.
- **API:** `CHHapticEngine.capabilitiesForHardware()` returns `any CHHapticDeviceCapability`. Its `supportsHaptics: Bool` is "whether the device supports haptic event playback" ([CHHapticEngine](https://developer.apple.com/documentation/corehaptics/chhapticengine.md), [CHHapticDeviceCapability](https://developer.apple.com/documentation/corehaptics/chhapticdevicecapability.md)). Also available: `init() throws`, `start() throws`, `stoppedHandler` and `resetHandler`.
- **Design:** Guard engine creation with `supportsHaptics`. Wrap `start()` in `do/catch`. Hide haptics behind a protocol and inject a no-op in UI tests. Do not assert on haptics in CI.

### 5. XcodeGen and the UI-test target
- **Verified syntax:** Target `type` accepts `application` and `bundle.ui-testing`. Scheme `testTargets` accepts plain strings, or objects with `name`/`target` and options such as `parallelizable` and `randomExecutionOrder` ([XcodeGen ProjectSpec](https://github.com/yonaskolb/XcodeGen/blob/master/Docs/ProjectSpec.md)).
- **Sketch (verify against your XcodeGen version):**

    deploymentTarget: "18.0"   # UNVERIFIED key placement

### Risks
1. **RealityKit rendering on the hosted VM (top UNVERIFIED risk).** A third-party CI vendor says its macOS VMs have no GPU acceleration, and an Apple forum shows "realitytool requires Metal" in build environments ([thread 763396](https://developer.apple.com/forums/thread/763396)). Both are indirect evidence. Add a preflight UI test that logs `MTLCreateSystemDefaultDevice()`. If it is nil, the RealityView screenshots will be blank.
2. **No iOS 18 runtime on the image.** The image lists only iOS 26.2, 26.4 and 26.5. Your iOS 18 deployment target is therefore not exercised on CI. Downloading an iOS 18 runtime is UNVERIFIED as a workaround.
3. **No iPhone 13 simulator.** The device list is iPhone 16e and the iPhone 17 family. Use an iPhone 17-class simulator as a proxy and test iPhone 13 on hardware.
4. **Simulator boot flakiness.** Secondhand runner-images issues report slow boots and simulators that never launch (no fetched primary source).
5. **xcparse on Xcode 26** is UNVERIFIED. Use native `xcresulttool` first.
6. **Accessibility audit scope.** Each named state needs its own audit call.

## Recommended approach
- Named states via launch arguments, one XCUITest per state, `performAccessibilityAudit` per screen with the iOS-applicable types.
- Screenshots as `XCTAttachment(screenshot:)`, exported with `xcresulttool export attachments` into an artifact folder, uploaded with `if: always()`.
- Motion and haptics injected behind protocols. No sensor or haptic assertions in CI.
- XcodeGen `bundle.ui-testing` target listed under the app's `scheme.testTargets`.
- Add a Metal preflight step before trusting RealityKit screenshots.
